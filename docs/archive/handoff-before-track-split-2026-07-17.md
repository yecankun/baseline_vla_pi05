# Handoff

Last updated: 2026-07-17

This file is the short execution handoff. Historical detail was archived in
`docs/archive/handoff-before-entry-slimming-2026-07-13.md`.

## Current Priority

Keep the project on the current mainline:

```text
simulation realism and real-system correspondence > BC rollout success
```

The active goal is not to make a small BC model look good in MuJoCo. The active
goal is now two-track:

- keep improving/using the real collection route;
- start VLA-style algorithm feasibility tests instead of waiting for perfect
  simulator alignment.

Algorithm results must still be labeled as feasibility until real data quality
and sim-to-real alignment improve.

Initial algorithm boundary:

- use small multimodal/VLA-style models first;
- prefer 3B or smaller when feasible, with 7B as the early-test upper bound;
- use openpi/pi0.5-style as the first practical pi-family baseline;
- add pi0.7-style context conditioning, initially through image-derived
  tactile/contact fields;
- include tactile-like input generated by visual collision/distance analysis
  from images;
- do not feed exact simulator contact/wall truth as tactile input.

Current algorithm status:

- The pi-style training pack and OpenPI-compatible 32D state/action adapter
  have both trained as smoke tests on the Ubuntu 4090 machine.
- The OpenPI-compatible adapter is only a framework-compatibility layer. Do not
  reinterpret its padded action dimensions as robot controls; the preferred
  target remains Elite TCP delta plus Piper discrete intent.
- Best reported 4090 OpenPI-compatible smoke epoch was 7/8 with
  `val_piper_acc=0.685`, `val_action_mae=0.3050`, and `val_elite_mae=0.3321`.
- Tactile/contact ablations currently look similar to the full-context run, so
  the present synthetic tactile fields are interface-ready but not yet proven
  useful.
- Tactile-signal audit found `estimated_contact_flag` is constant zero over
  the current pack. Confidence and image-distance vary, but are weakly
  correlated with Piper feed labels and Elite movement scale.
- A posthoc contact-rich pack with about `15%` positive contact-like flags
  still did not show a clear full-context advantage over `drop_tactile_all`.
  Treat tactile/contact context as an interface requirement, not a proven
  performance gain on the current dataset.
- A small LeRobotDataset export smoke passed on the Ubuntu 4090 machine using
  `tools/export_openpi_compat_to_lerobot.py`. The exporter preserves
  `elite_tcp_delta_6d` and `piper_intent_id` as explicit project targets.
- A LeRobotDataset-loader smoke model trained successfully on the full exported
  dataset using `tools/train_lerobot_compat_smoke.py`, so the official loader
  path is verified before OpenPI model work.
- The official LeRobot PI05 adapter path has passed preprocess and
  forward/backward probes on the Ubuntu 4090 machine using
  `tools/probe_pi05_lerobot_adapter.py`. The successful forward/backward
  configuration is `paligemma_variant=gemma_2b`,
  `action_expert_variant=gemma_300m`, `dtype=bfloat16`,
  `freeze_vision_encoder=True`, `train_expert_only=True`, and
  `gradient_checkpointing=True`; the probe reported `loss=1.4252` and valid
  gradients. This confirms interface feasibility only.
- PI05 adapter training has passed a micro-batch overfit diagnostic. The first
  40-step shuffled smoke did not improve validation (`1.4671` to `1.5115`),
  but the fixed-noise repeated-batch run reduced train loss from `1.2840` to
  `6.55e-05` over 80 steps. Treat this as proof that the optimizer/model/data
  path is functional, not as evidence of policy quality.
- A 300-step normal PI05 adapter-training smoke with episode-level split and a
  fixed evaluation seed showed stable validation reduction:
  `initial_val_loss=1.4810`, `final_val_loss=0.9837`, train/val samples
  `1649/399`. This establishes PI05 sim-data trainability on the current
  LeRobot export, still only as algorithm feasibility.
- A checkpointed 1000-step PI05 adapter run completed on the Ubuntu 4090
  machine and saved `final_policy.pt`. Validation loss decreased from
  `1.4696` initially to `0.3158` at step 1000, with every 100-step validation
  point lower than the previous one after step 100. This is stronger sim-data
  trainability evidence, but the next required check is held-out open-loop
  action prediction rather than another loss-only run.
- Full held-out open-loop sampling from `final_policy.pt` is not yet strong:
  over `616` validation samples, Piper argmax accuracy was `0.5032` versus a
  majority baseline of `0.5292`; Elite TCP-delta MAE had mean `0.6283` and
  median `0.2451`. Treat this as a negative mixed-action decoding result, not
  as a failure of the dataset loader or training loss path.
- Re-running the same held-out diagnostic with `--num-inference-steps 50` did
  not materially improve the result: Piper accuracy was `0.5081` versus the
  same `0.5292` majority baseline, and Elite TCP-delta MAE remained similar
  (`mean=0.6296`, `median=0.2472`). Treat inference-step count as tested; the
  next likely fix is action-head semantics.
- `tools/probe_pi05_feature_interface.py` verified the installed LeRobot
  `0.4.4` source contract on the 4090 machine. Its PI05 forward and sampling
  paths use images and language but ignore `observation.state`; current
  official PI05 results therefore do not yet test robot-state or tactile
  conditioning in the Elite diffusion branch.
- `tools/train_pi05_mixed_head_adapter.py` and
  `tools/eval_pi05_mixed_head_open_loop.py` now provide the first explicit
  mixed-action path. Elite reuses the frozen 1000-step checkpoint, while Piper
  is classified from PI05 prefix embeddings plus normalized state. A 2-step
  train smoke and 2-record held-out smoke passed remotely, but the validation
  smoke contained only one Piper class and is not a model-quality result.
- The full 1000-step frozen-head run did not beat its baseline. Train/validation
  Piper supports were `[0, 1660, 1820]` and `[0, 60, 68]`; final accuracy was
  `0.53125`, equal to the majority baseline, balanced accuracy was `0.5`, and
  the classifier predicted every validation record as class 2. Intermediate
  checkpoints only alternated between all-class-1 and all-class-2 collapse.
- The base checkpoint used by that run is not a pretrained PI05 model. The
  current script constructs `PI05Policy(config)` without `from_pretrained` and
  freezes the randomly initialized PaliGemma path. The 4090 cache has no
  `lerobot/pi05_base` entry. Treat all results from this base as architecture
  and optimizer feasibility only.

## Current Mainline

- Mainline collector: `simulation.collect_formal_tip_line_guidance`.
- Mainline guidewire: tip-centric / hard-elastic, continuous line-shaped visual.
- Mainline Elite magnetic target: front-up relative to the guidewire tip or
  registered route point; avoid regenerating/exporting data with a directly
  overhead magnetic target.
- Default formal start:
  `--start-fraction-min 0.42 --start-fraction-max 0.54`.
- Formal collection/eval should fail closed with `--formal-data` /
  `--formal-eval` when an oracle mechanism is used.
- Current real-data entrypoint: `data/collect/collect_real_shadow_pilot.py`.
- Current real-capture video tool: `tools/render_real_shadow_video.py`.

Target policy/controller split:

```text
observation + task instruction -> Elite TCP delta + Piper discrete intent
```

The controller handles Elite IK/joint execution, Piper command timing,
cooldowns, bounds, safety, and executed-command logging.

## Do Next

If continuing locally:

1. Use the July real captures as calibration/alignment anchors.
2. Improve simulator correspondence around guidewire entry geometry, visual
   domain, Piper feed event scale, Elite motion scale, and observable
   contact/tip estimation.
3. Implement and verify loading of the reproducible `lerobot/pi05_base`
   pretrained checkpoint before another mixed-head run. Record loaded/missing
   keys and checkpoint provenance. Then compare `state_only` with balanced
   `prefix_state` Piper features before injecting state/tactile tokens into the
   Elite diffusion path. Do not run full evaluation on the collapsed v1 head.
   Add real-domain calibration anchors before claiming sim-to-real transfer.
4. Keep formal synthetic-data generation free of hidden MuJoCo truth.
5. Use BC rollouts only as regression checks after simulator/data changes.

If returning onsite:

1. Verify camera IDs, warmup, and synchronization.
2. Verify CAN/Piper or feeder bring-up before collection.
3. Test physical guidewire delivery first; stop early if the guidewire path is
   still mechanically unreliable.
4. If the original physical method still cannot collect usable data, try a
   vessel model without the S-bend.
5. Treat new captures as calibration data until they are visually and
   mechanically accepted as clean demonstrations.

If updating docs:

- Update only the smallest relevant docs.
- Put durable weekly/reporting facts in `docs/weekly-meeting-log.md`.
- Archive historical detail instead of keeping entry files long.

## Do Not Do

- Do not optimize small BC performance as the main research path.
- Do not delay all algorithm work until the simulator is perfect.
- Do not accept rollout success that depends on oracle tip/wall/contact/route
  state.
- Do not use `branchs/` as guidewire centerline or trajectory supervision.
- Do not treat July real captures as clean expert data by default.
- Do not make strong Piper wallguard/hold/away correction a formal mechanism
  without a real observable and real controller path.
- Do not migrate to Isaac Sim as the default physics/control route unless the
  user explicitly changes direction.
- Do not update every doc after every chat turn.

## Current Caveats

- Real guidewire delivery is still the main hardware blocker.
- Removing the physical S-bend helped but did not solve delivery.
- UDP feeder control works but is fallback/debug only.
- Piper/CAN failures should be diagnosed at the device/interface level before
  assuming a Python bug.
- Image-domain realism still differs from real glass-vessel captures through
  blur, reflection, lighting, and camera placement.
