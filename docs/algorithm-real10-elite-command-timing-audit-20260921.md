## 关键时序纠正

Collector在后台线程中先计算IK，再调用`move_joint`，**调用返回之后**才更新目标、索引和
`elite_path_command_timestamp`。主循环先取Side/Top和Elite位姿，再提交键盘请求。因此：

1. 请求行图像/位姿可作为请求前观测，但该行的目标快照可能尚未更新；本批175次全部如此。
2. 不能将`elite_path_command_timestamp`当发送时刻或动作起点。
3. `reference_action.elite_tcp_delta_6d`仍是`finalize_record`写入的下一帧实测位姿差，
   可沿用其既有BC目标语义，但不能当动作前已知命令。

进一步只读检查远端现装 `sam3/.../site-packages/elite/_move.py`：`move_joint`默认
`block=True`，收到发送成功后调用`__wait_stop()`，等机器人状态离开PLAY才返回。
这比旧审计的“发送后时间戳”更具体：**在这套SDK下，该字段是阻塞调用返回后的时间**。
SDK不是采集当时冻结的版本，故只将当前实现和原始时序的吻合列为证据，不伪称历史版本已验证。

日志支持这一解释：

- 请求时间上界到该时间戳的中位间隔 **1.826 s**，范围 **1.332–2.216 s**。
- **161/175**次该时间戳落在请求后的名义1.5秒窗口之外。
- **171/175**次在该时间戳之前，已经有完整记录可用、且实测xyz距请求目标不超过1mm。
  这里1mm仅作时序诊断，**不是新的到位标准**，也不证明姿态收敛或导丝推进。

`__wait_stop`也会在暂停、错误、碰撞等非PLAY状态退出；collector没有保存普通
`move_joint`返回值或最终机器人状态。因此`move_joint_sent`不是可靠的接受/成功/到位证据，
不能由阻塞行为推断175次均执行成功。内部`elite_path_command_busy`也未写入这些records。

请求括区用“Side/Top host时间与Elite查询开始时间的最大值”至`piper_action`时间构成，
宽度中位 **3.84ms**、最大 **101.17ms**；这是**程序顺序约束的提交括区**，不是机器人起动
时刻。Elite时间戳在RPC查询前记录，不是精确的测量返回/输入就绪时刻；相机是host接收
时间，不是硬件曝光同步。CSV的timestamp在图像落盘之后，不能额外补出发送或完成时间。

## 可以复用什么，不能复用什么

可保留的监督单位是：

`请求前双视角/实测状态与历史 + 原始绝对目标请求和运动模式 → 后续图像/实测响应`

动作类别必须写明`absolute_tcp_target_to_IK_to_move_joint`。保留xyz毫米/rpy弧度、
原始IK关节目标、速度参数20；现装SDK将速度解释为关节速度百分比，不能当作20mm/s。
IK关节值在工件中保持SDK原生值，未自行转换或猜测其单位。相对锚点的目标xyz差只放
审计字段，不写入`elite_tcp_delta_6d`，不改变`observation + task → elite_tcp_delta_6d + piper_intent_id`。

所有175个Elite请求锚点的Piper请求均为hold=1；不代表导丝物理静止。166个有可用的
前一条控制器历史，9个位于episode起点而缺失；其中1个历史显示Piper仍busy。名义
1.5秒内保留5或6条未来帧记录：以**实际最后一张响应图时间**为界，2窗有后续Piper feed
请求，0窗有边界交叉请求。这些均保留并单列，不按响应好坏删样本；其余173窗也不能
自动称为纯单动作因果样本。该统计不是整个连续1.5秒内绝无其它动作的保证。

旧人工标签描述原完整窗口，只有UI49完全匹配新请求窗；**不复制45个标签到新窗、不把
Elite位移当导丝advance标签、不从缺失标签补stationary**。本轮不新标注、也不重算识别效果。
未来可先用未来图像/表征或实测Elite响应做观测性监督，不要求立刻人工补标175窗；如果
继续使用advance/stationary指标，则需要对应窗口的人审，不能借用旧窗标签。

仍然只有10条相关轨迹，不是175条独立轨迹；这些轨迹已被现场PI05使用，不是独立PI05
验证集。path index、episode ID、事后状态、实际执行时长不作为预测输入；如定义新训练包，
名义预测时域应预先固定，未来信息只作监督/审计。
