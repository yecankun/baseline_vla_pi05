# Real Control Bandwidth Plan

Last updated: 2026-06-18

## Why This Exists

The current Elite jitter problem should not be solved by repeatedly adding
arbitrary smoothing. The purpose of simulation is to generate data that remains
meaningful for the real system. Therefore any control-side smoothing, rate
limit, or interpolation should be justified as an approximation of the real
Elite/magnetic-arm control bandwidth.

This document defines the next engineering direction: use real `branchs` pose
motion as a bandwidth anchor, then make MuJoCo rollout diagnostics and control
execution match that anchor as closely as practical.

Important semantic constraint:

```text
Real branch pose = Elite/magnetic-arm motion, not guidewire trajectory.
```

Use it to sanity-check robot/magnetic motion scale, not as guidewire-tip
supervision.


Interpretation:

- The real Elite/magnetic-arm visible motion has a position-step p95 around
  `5 mm/frame`.
- Real pose sequences have very few direction reversals, so high-frequency
  back-and-forth motion in simulation is suspicious even if the step size is
  numerically capped.
- A large fraction of real frames have zero pose step, so the real controller or
  logging stream may contain hold/intermittent-update behavior.
- The real Piper labels are binary stop/advance commands (`0=stop/hold`,
  `1=piper.step_forward(...)`), which remains a separate semantic gap from
  continuous simulated feed/retract `piper_feed`. Retract is still a plausible
  real-control requirement; it needs an explicit real command and label rather
  than being inferred from the senior two-class Piper BC data.

## Negative Results to Preserve

Do not repeat these as if they are unsolved first attempts:

- `rate010_r1` made visible `elirobot_pose` p95 close to the real step anchor
  (`~5.78 mm` versus real `~5.07 mm`) and preserved task success, but video
  still showed jitter.
- `rate010_smooth025_r1` reduced visible step p95 further (`~4.37 mm`) but video
  review was only slightly better. More rollout-time smoothing is not the main
  path.
- Naive `elite_action_representation=delta` reduced target-jump p95 but caused
  visible Elite tool drift around `24-28 cm`, so unconstrained accumulated
  deltas are not acceptable.

## Next Engineering Objective

Implement a real-bandwidth diagnostic layer before adding another controller
variant.

The diagnostic should compare each rollout against real bandwidth anchors using:

- visible `elirobot_pose` step p95 and max;
- visible `elirobot_pose` acceleration p95;
- visible `elirobot_pose` jerk p95;
- direction reversal fraction;
- zero or near-zero step fraction;
- `magnetic_pose` step/acceleration/jerk;
- `tip_to_elite_tool` and `tip_to_magnetic` drift.

The existing `tools/analyze_mujoco_elite_rollout.py` already covers joint jumps,
tool steps, magnetic steps, and tip distances. The missing piece is a
real-bandwidth comparison report that makes sim rollout motion comparable to:

```text
simulation_output/real_control_bandwidth/real_control_bandwidth_summary.json
```

Implementation:

```text
tools/compare_rollout_control_bandwidth.py
```

The script writes JSON, CSV, and Markdown summaries. It compares rollout
`elirobot_pose`, `magnetic_pose`, and sim-only `tip_pos` against the real
bandwidth anchor. It converts rollout meters to millimeters before comparison.

Initial validation output was written to:

```text
docs/_rollout_control_bandwidth_check
```

Key result:

```text
v2 rollout elirobot: step_p95 10.065 mm, accel_p95 10.507, jerk_p95 16.144
rate010_r1 elirobot: step_p95 5.777 mm, accel_p95 6.013, jerk_p95 7.947
rate010_smooth025_r1 elirobot: step_p95 4.369 mm, accel_p95 4.439, jerk_p95 5.766
```

Interpretation:

`rate010_smooth025_r1` is close on step p95 but still high on jerk and direction
reversal, matching the user's video observation that it is only slightly better.

## Candidate Control Layer

After the diagnostic exists, implement a controller that models real execution
instead of arbitrary smoothing. Preferred design:

1. Keep the learned external action schema as `piper_feed_elite_joint`.
2. Treat the model output as a desired Elite six-joint target.
3. Add a rollout execution layer that applies bounded joint velocity and,
   if needed, bounded acceleration or jerk.
4. Tune the bounds against real visible pose bandwidth:
   - position step p95 near `5.07 mm/frame`;
   - acceleration p95 near `2.98 mm/frame^2`;
   - jerk p95 near `2.84 mm/frame^3`;
   - direction reversal fraction near zero.
5. Reject settings that preserve task success only by letting the visible Elite
   tool drift far away from the guidewire/magnetic point.

This is different from simply increasing `--elite-motion-smoothing`: the control
layer should be evaluated as a proxy for real robot bandwidth, with measurable
acceptance criteria.

Implementation update:

```text
simulation/mujoco_guided_wire_env.py
simulation/eval_mujoco_guided_wire_rollout.py
```

Rollout now supports:

```text
--elite-joint-accel-limit
```

This limits the per-step change in the executed Elite joint delta. It should be
used together with `--elite-joint-rate-limit`, starting with:

```text
--elite-joint-rate-limit 0.010
--elite-joint-accel-limit 0.002
```

If task success and drift remain acceptable but visible jerk stays high, test:

```text
--elite-joint-rate-limit 0.010
--elite-joint-accel-limit 0.001
```

## Acceptance Criteria

A rollout/control variant is a useful reference only if:

- left and right tasks still succeed;
- visible Elite motion is close to real bandwidth on step, acceleration, jerk,
  and direction reversals;
- `magnetic_pose` remains smooth and continues to guide the simulated tip;
- `tip_to_elite_tool` does not drift into the large-error regime seen in the
  naive delta model;
- the video no longer shows obvious high-frequency Elite jitter;
- the change preserves the external `piper_feed_elite_joint` interface.

## Current Next Step

Build the sim rollout bandwidth comparison first. Then use it to choose between:

- a joint velocity plus acceleration-limited execution layer;
- bounded/rate-limited Elite target training;
- a hybrid model that predicts residuals while staying anchored to an absolute
  Elite target.

Do not continue with larger smoothness weights or tighter low-pass smoothing
unless the change is explicitly justified against the real bandwidth report.
